# Update matkv.dev

matkv.dev is generated by VaultContentGen from markdown notes in Matko's Obsidian vault. Content changes are made by editing those notes and then running the generator, never by hand-editing generated site output.

## Where this runs

This workflow needs Matko's own machine: the `dotnet` runtime, the release binary and the absolute `/home/matko/...` paths in the config. Run it from Claude Code in his normal shell. If you're in an environment where those paths or `dotnet` don't exist (for example a sandboxed or remote shell), you can still make the confirmed note edit, but stop before `generate` and tell Matko to run it himself. Don't install tools, rewrite the config or hand-edit generated content to work around this.

## Locating things

1. VaultContentGen folder: `/home/matko/dev/VaultContentGen`. Its `CLAUDE.md` documents the commands and options; check it if anything below looks out of date.
2. Config: `~/.config/VaultContentGen/config.json`. Always read the paths from it; never hardcode or guess them, and don't ask Matko unless the config is missing or unreadable. Relevant keys:
   - `VaultSourcePath`: the `Notes/matkv.dev/` folder itself (not the vault root). This is where source notes live.
   - `HugoContentPath`: the `content/` folder of the matkv.dev Hugo repo. `generate` writes here; the git repo is its parent folder.
   - `BookSourcePath` / `MovieSourcePath`: vault folders the individual book and movie/TV entries are pulled from.
3. Release binary: `/home/matko/dev/VaultContentGen/src/VaultContentGen/bin/Release/net10.0/vaultcontentgen`.

## Rules

- Edit only files inside `VaultSourcePath` (`Notes/matkv.dev`). Section pages and index pages, such as the book list intro in `Library/Books/Index.md`, live there.
- A change to a single book or movie/TV entry lives in `BookSourcePath` / `MovieSourcePath` instead. Only edit those when the request is about that specific entry, and say so when you do.
- Do not touch other vault folders, the VaultContentGen code, or the generated output in the Hugo repo by hand.
- Never change a vault file before Matko has confirmed the proposed change (workflow step 2).
- Preserve the frontmatter conventions of neighbouring notes. Look at a few existing notes in the folder before creating a new one, and follow their structure and naming.
- Keep Obsidian-style content intact (wikilinks, embeds, callouts) unless Matko asks to change it.
- Write in the language and tone the existing note already uses.
- Edit files in place with a targeted replacement; don't retype a whole note from earlier output.

## Workflow

1. Find the note(s) to change and read them. Don't edit anything yet.
2. Show Matko what you would do and **ask for confirmation** before touching the vault:
   - the full path of each file you'd change, create, rename or delete
   - for edits, the exact before/after of the affected lines (a small diff-style snippet, not the whole note)
   - for new notes, the full proposed content including frontmatter
   Only make the change once he approves. If he wants something different, revise the proposal and ask again.
3. Make exactly the confirmed change in the vault.
4. Run the **release** binary with `generate --no-serve`:
   ```bash
   /home/matko/dev/VaultContentGen/src/VaultContentGen/bin/Release/net10.0/vaultcontentgen generate --no-serve
   ```
   `--no-serve` only writes the content and exits. Never run plain `generate` here: it also deletes the site's `public/` folder and starts `hugo serve`, which blocks. Never use the debug build or `dotnet run`. If the binary is missing, ask Matko instead of building or substituting another version. A non-zero exit code means it failed: show Matko the output and stop; don't work around it.
5. Show Matko the diff (`git diff`, plus `git status` for new or deleted files) in the matkv.dev repo, and in the vault too if it is a git repo. `public/` is gitignored and can be ignored. **Ask for confirmation.** Do not commit before he approves. If he wants changes, propose them (as in step 2), adjust, re-run `generate --no-serve` and show the diff again.
6. Propose a short commit message (imperative, lowercase, one line; check `git log` for the existing style) and **ask for confirmation**. Commit only the files that belong to this change, in each touched repo.
7. After the commit is confirmed, push to the current branch's remote. Never force-push. If the push fails, report the error and stop.
8. Finish with one line: what changed and that it was pushed. Mention that Matko can preview locally with plain `vaultcontentgen generate` (which runs `hugo serve`) if he wants to.
